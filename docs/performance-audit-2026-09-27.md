**Waystone: исследование архитектуры и производительности — 27 сентября 2026**

Исторический снимок до исправлений. Описанное ниже поведение относится к указанным ревизиям; последующие изменения описаны в README и истории Git.

Главный вывод: текущий gateway уже работает за пределами комфортного бюджета памяти. Но дело не просто в количестве страниц: есть воспроизведённая проблема открытия индекса Whoosh, лишняя подсветка тысяч результатов и расточительная индексация. Сначала стоит исправить эти места и жизненный цикл crawler, затем выбирать размер сервера. Заменять движок первым шагом необязательно.

Изменения в приложение и конфигурацию сервера не вносились. На gateway выполнены короткие диагностические команды, прочитаны логи и сделана временная SQLite backup-копия; после скачивания временный файл удалён. Нагрузочные эксперименты выполнены локально. В репозиторий добавлены только исследование, обезличенные результаты измерений и воспроизводимый probe.

**Что именно проверено.**

Прочитаны поиск, rerank, crawler, RNS-обвязка, планировщик, SQL-модели и запросы, обработчики страниц и шаблоны. Прослежены вызовы от RNS до ответа и от обнаружения ссылки до записи индекса. Gateway найден по заметке `~/brain/entity/infra/server/gateway.md`, доступ проверен по SSH.

Локальная ревизия — `da3b592645e04da94096511b5f40e5acf0d118b6`, серверная — `2ddeb1ffff1972ccbfe055e26c64129412b0cde2`. Сравнение исходников `src` обнаружило единственное отличие: срок удаления узлов по умолчанию 14 дней локально и 30 на сервере. Серверный `start.sh` также отличается и действительно запускает `python -m src.main` из venv. Поэтому выводы о поиске и crawler относятся к работающей версии.

Сервер: Python 3.10.12, Whoosh 2.7.4, SQLAlchemy 2.0.46, NumPy 2.1.3, SciPy 1.15.3, RNS 1.0.0, пять потоков crawler, LOG_LEVEL=INFO. Локальные эксперименты: Python 3.11.15, те же версии перечисленных библиотек, Intel Core Ultra 7 255H, без swap pressure, OPENBLAS_NUM_THREADS=1. **Локальные секунды нельзя выдавать за задержку ответа на VPS или в Reticulum.** Сеть, шаблон ответа, SQL-запись истории и очередь входящих запросов в поисковый benchmark не включены.

SQLite скопирована через backup API; файлы Whoosh прочитаны из работающего индекса. Локально открыты все сегменты и прочитаны все живые документы без ошибок. Это пригодный для исследования снимок, но не атомарная общая транзакция SQLite+Whoosh. Большие масштабы поиска ниже — расчётная экстраполяция, не нагрузочный тест VPS на 70 тысячах страниц.

Причинную долю SSH/system maintenance и текущей работы приложения этим снимком разделить нельзя; авария показывает отсутствие запаса даже для обычных административных операций. Waystone делит машину с rnsd, Docker/containerd, nginx-proxy-manager, TorrServer, Glances и другими процессами. В одном снимке у rnsd было примерно 219 MiB RSS и 167 MiB VmSwap. У Glances — около 23 MiB RSS и 108 MiB VmSwap. Это не измерение уникальной памяти всей системы и не повод складывать VmSize, но очевидно, что все 454 MiB приложению не принадлежат.

В истории SQL всего 12 записей первой страницы поиска за последние сутки снимка, 54 за неделю, 1 227 за 30 дней. Это не полный счётчик RNS-трафика: сюда не входят остальные страницы/ошибки/другие endpoints. Однако накопленные данные не подтверждают объяснение «просто слишком много одновременных пользователей».

**3. Первое узкое место: открытие Whoosh searcher копирует сотни мегабайт.**

[SearchEngine открывает FileStorage с настройками по умолчанию](../src/core/search/search_engine.py#L49). В Whoosh 2.7.4 цепочка такая:

`FileStorage(supports_mmap=True) → CompoundStorage.open_file → BufferFile(memoryview) → BytesIO(buf)`.

Последний шаг создаёт копию содержимого вложенного файла сегмента. Поэтому здесь mmap не означает «индекс остаётся на диске и читается по требованию». Проверено по исходникам установленного Whoosh и `tracemalloc`: при открытии searcher около **239 MiB Python-аллокаций** приходится на `structfile.py:357`, `self.file = BytesIO(buf)`. Дополнительно RSS включает прочитанные страницы mmap.

Отдельный свежий процесс, тот же индекс и запрос `network`, без предварительного сканирования корпуса:

| Этап | По умолчанию, RSS | `supports_mmap=False`, RSS |
|---|---:|---:|
| Импорт поискового модуля | 130.9 MiB | 130.7 MiB |
| Только открытие searcher | 609.2 MiB | 131.1 MiB |
| Получены поля 2 696 совпадений | 658.9 MiB | 133.7 MiB |
| Пиковый RSS данного эксперимента | 661.3 MiB | 136.2 MiB |

Это воспроизводится **до подсветки, rerank и заполнения query cache**. Даже запрос без совпадений платит за открытие searcher; локально это добавляло около 90 мс, а на переполненном swap эффект гораздо хуже. Writer также открывает readers при обновлениях/слияниях, поэтому настройки хранения важны не только для входящего поиска.

Первое предложение — создавать FileStorage с `supports_mmap=False` в обеих ветках открытия/создания индекса. Формат индекса не меняется, переиндексация для этой настройки не нужна. Это штатный параметр [FileStorage](https://whoosh.readthedocs.io/en/latest/api/filedb/filestore.html); источник копирования — [Whoosh 2.7.4 BufferFile](https://github.com/mchaput/whoosh/blob/v2.7.4/src/whoosh/filedb/structfile.py).

Это существенно снижает потребность поиска в памяти, но **не гарантирует**, что shared gateway с rnsd и остальными сервисами станет устойчивым на 454 MiB. Нужна повторная проверка суммарного потребления, включая crawl и merge.

**4. Второе узкое место: подсветка всех совпадений перед пагинацией.**

Текущий путь в [search_engine.py](../src/core/search/search_engine.py#L131), [rerank.py](../src/core/search/rerank.py#L23) и [views.py](../src/core/views.py#L215):

1. OR-поиск по пяти полям с `limit=None`.
2. Загрузка stored fields и создание SearchResult для каждого совпадения.
3. Подсветка текста каждого совпадения.
4. Удаление дублей URL и ограничение до двух страниц на адрес.
5. SQL-признаки узлов, вероятность доступности, новое ранжирование.
6. Сохранение всей выдачи в cache.
7. Только затем выбор 20 результатов нужной страницы.

`fragmenter.maxchars=100` ограничивает размер фрагмента, а не количество обрабатываемых результатов или загружаемый текст. В установленной версии Whoosh `charlimit=32768`; подсветка обычно повторно токенизирует до этого предела, но stored text читается целиком. Поэтому было бы неточно называть подсветку обязательным проходом по всему тексту каждой большой страницы.

Три повторения каждого варианта на локальном снимке; медианы в секундах, исходный вариант с mmap. Это воспроизведение pipeline, а не end-to-end SLA:

| Запрос | Совпадений → после фильтров | Сейчас | Подсветка только top-20, полный rerank | Top-200 BM25, затем rerank и top-20 |
|---|---:|---:|---:|---:|
| `reticulum` | 2 474 → 783 | 1.274 | 0.196 | 0.120 |
| `test` | 1 107 → 375 | 1.095 | 0.152 | 0.108 |
| `network` | 2 696 → 546 | 1.648 | 0.194 | 0.121 |
| `page` | 13 252 → 1 337 | 8.110 | 0.490 | 0.153 |

В повторной серии **без mmap и с поздней подсветкой** получено 0.112 с для `network` и 0.418 с для `page`, при сохранении прежнего top-20. Это примерно ×15 и ×19 относительно исходного pipeline с mmap на этих запросах.

В исходном `network` непосредственно подсветка занимала около 1.44 с; rerank — 0.026 с. Для `page` подсветка — 7.57 с, rerank — 0.065 с. Поэтому оптимизировать NumPy вместо порядка операций сейчас невыгодно.

Поздняя подсветка сохранила состав и порядок top-20 на всех четырёх запросах. При отключённом mmap её общее время составляло примерно 0.06–0.52 с в первоначальной серии; точные повторные результаты сохранены отдельно. **Обе оптимизации нужны вместе:** перенос подсветки почти не устраняет огромную аллокацию при открытии searcher, а отключение mmap не устраняет секунды токенизации.

Top-200 — уже изменение алгоритма. Пересечение со старым top-20: `reticulum` 20/20, `test` 19/20, `network` 15/20, `page` 19/20; даже при 20/20 порядок может измениться. Причины: часть кандидатов отброшена, min-max нормализация зависит от всей выборки, ограничения по адресам применяются после top-K. Один большой сайт способен занять значительную часть первых K мест.

Поэтому порядок исправлений: сначала поздняя подсветка с сохранением полного ранжирования; затем, если нужна дополнительная экономия, top-K с явным ограничением глубины выдачи и оценкой релевантности. Кандидатный бюджет 200–500 — старт эксперимента, не доказанный оптимум. Для более полного покрытия можно набирать кандидатов с учётом разнообразия адресов, но это отдельное усложнение.

Пагинация должна работать с компактными метаданными/идентификаторами; текст и snippets получать для выбранной страницы. При хранении docnum нужно учитывать поколение индекса: после merge docnum может поменяться. Практичнее хранить стабильный URL плюс версию cache и заново находить документ при необходимости.

**5. Входящий поиск может задерживать сам приём пакетов.**

NomadAPI вызывает обработчик синхронно. В установленном RNS 1.0.0 обычный короткий REQUEST проходит через `LocalInterface.process_incoming → Transport.inbound → Link.receive → Link.handle_request → response_generator`. Здесь нет автоматической передачи каждого такого запроса в независимый worker.

Следствие для обычного shared-instance подключения: пока этот callback подсвечивает тысячи документов, соответствующий поток чтения локального интерфейса не обрабатывает следующие кадры. Это может задержать и ответы crawler, и другой трафик этого клиента. Для resource-based запросов путь может отличаться; не следует обобщать это на абсолютно все варианты RNS. Проверено чтением кода библиотеки, **временная корреляция с сетевыми таймаутами на production не измерялась**. [Исходник RNS 1.0.0 Link](https://github.com/markqvist/Reticulum/blob/1.0.0/RNS/Link.py).

Исправление сначала — сделать callback коротким. При дальнейшем разделении нужны ограниченное число выполняемых запросов и корректная интеграция асинхронной обработки/отправки ответа на границе RNS. Просто запустить поиск в thread/process и тут же ждать `.result()` в том же callback недостаточно: приём останется заблокирован. Неограниченный thread-per-request на этом сервере особенно опасен.

**6. Parser и cache позволяют дорогую работу без верхнего предела.**

MultifieldParser принимает не только слова, но и сложные выражения. Локальный запрос `*` с отключённым mmap не завершился за установленный лимит **30 секунд**; отдельный прерванный запуск находился ещё в сборе совпадений, до подсветки. Одного ограничения K недостаточно для гарантированного времени: раскрытие wildcard и построение matcher могут быть дорогими сами по себе.

Нужны явные пределы длины запроса, числа терминов/операторов, `page_size`, глубины выдачи и параллелизма. Самый простой продуктовый вариант — обычный поиск по словам/фразам с отключённым произвольным wildcard-синтаксисом; если расширенный синтаксис нужен, ему требуются отдельные лимиты. Timeout потока Python сам по себе не останавливает уже начавшуюся CPU-работу.

[Cache](../src/core/search/search_engine.py#L177) ограничен 200 ключами, но не байтами. На снимке результат `page` после фильтров занимает около 1.29 MB Python-объектов, `network` около 0.46 MB. 200 таких разных ключей — потенциально порядка 90–260 MB только результатов, без временных данных и служебных структур. Это оценка потенциального накопления, а не измеренный размер cache работающего сервиса.

TTL не удаляет просроченные записи сам: они живут до повторного обращения к тому же ключу или LRU-вытеснения. Cache hit копирует список целиком, O(R), а не O(1). Копия поверхностная; `views.search` меняет разделяемые SearchResult. `highlight` не входит в ключ, успешная индексация cache не инвалидирует, одновременные промахи одинакового запроса не объединяются.

Предлагается cache компактной выдачи с бюджетом по памяти, реальным удалением expired записей, ключом с версией индекса и параметрами поиска, ограничением одновременных miss. Не стоит начинать с увеличения TTL или Redis: первичную стоимость запроса это не исправляет, а память сейчас важнее hit rate.

**7. Индексация регулярно переписывает весь индекс.**

[Батч — всего 10 документов, каждые 25 батчей выполняется `optimize=True`](../src/core/search/search_engine.py#L40). То есть полное слияние примерно каждые 250 страниц, иногда чаще по числу страниц из-за неполных flush. Обычные commits тоже могут выполнять автоматические небольшие merges.

При условном полном обновлении 14 198 страниц — примерно 1 420 commits и 56–57 полных optimize. Если стабильный индекс около 263 MiB, грубый объём перезаписи при полных merge — порядка **15 GiB за такой проход**, плюс чтение, новые сегменты и другие записи. Это модель write amplification, а не измеренный дисковый трафик данного обхода. На существующем индексе с ростом корпуса ×3 это около ×9 работы полных merge; при ×5 — около ×25, если сохранить частоту optimize и обновлять все страницы.

Каждая успешно скачанная страница переиндексируется независимо от изменения текста. `update_document` удаляет старую запись и добавляет новую; это не сравнение содержимого. Во время writer.commit удерживается общий lock, поэтому остальные downloader, дошедшие до queue_document, ждут. [Поведение update_document и merge описано в Whoosh](https://whoosh.readthedocs.io/en/latest/indexing.html).

`ix.writer()` использует стандартный `limitmb=128`. Это бюджет pool, а не жёсткий предел RSS; библиотека отдельно предупреждает об overhead Python. Для машины 454 MiB настройка слишком оптимистична, особенно одновременно с поиском и rnsd. [Документация limitmb](https://whoosh.readthedocs.io/en/latest/batch.html).

Минимальные изменения: убрать периодический full optimize из обычного crawl; оставить стандартные merges, редкое обслуживание запускать по измеренным сегментам/deletions. Задать меньший writer pool, например начать проверку с 16–32 MiB. Батчи ограничить одновременно числом документов, байтами и временем ожидания; не просто увеличить 10 до 1000. Сохранять hash индексируемого содержимого/метаданных и не переписывать неизменившиеся страницы.

`raw` повторно сохраняет `doc.text` и нигде в проекте не используется для чтения. У 14 087 из 14 198 документов `raw == text`, остальные вероятно записаны иной прежней схемой/логикой. Удаление лишнего stored поля уменьшит хранение/декодирование, но не обязательно вдвое из-за сжатия. Нужна управляемая миграция/reindex, после проверки старых записей.

Поле nodeName использует ngram длиной 4–15 и повторно индексируется на каждой странице узла. Для одного слова из 20 символов это 138 вхождений ngram до учёта повторов. Это увеличивает индекс/число postings; при переиндексации стоит проверить, нужен ли substring-поиск по именам в таком виде, или достаточно отдельного компактного индекса узлов. Менять анализатор без оценки качества не предлагается.

Ещё два риска writer: `delete_by_address` обходит общий writer lock и делает full optimize; в `_flush_index_queue_locked` очередь очищается до успешного commit. Ошибка writer может потерять пакет до следующего удачного обхода, а visited уже выставлен. Нужны единый владелец writer, cancel/cleanup при ошибке и удаление батча из очереди только после успешного сохранения.

**8. Crawler тратит ресурсы на неподходящие URL и может зависать/перекрываться.**

[extract_links](../src/core/crawler/parser.py#L10) считает внешней практически любую ссылку с `:`, если она не начинается с `:`. Проверка `.mu` находится позже, в [load](../src/core/crawl.py#L73), после попадания в очередь и SQLite visited. Это допускает `https:`, `http:`, ссылки на файлы, формы и произвольные параметры.

Подтверждено данными: 12 808 visited URL начинаются с HTTP(S), 33 865 вообще не содержат `.mu`. В двух скопированных crawler-логах 6 382 предупреждения о полной очереди, из них 5 805 относятся к HTTP(S). Это не 6 382 уникальные потерянные Reticulum-страницы, но реальное давление ненужных ссылок на очередь, транзакции и логирование.

Фильтровать надо **перед visited/queue**: валидный 32-символьный hex destination, разрешённый путь страницы, понятная политика параметров. Отбрасывать фрагменты и канонизировать URL там, где это не меняет смысл страницы. Ограничить длину URL, размер ответа/число ссылок на страницу и бюджет страниц узла. Сейчас одна страница до 1.5 MB уже есть; несколько одновременных крупных ответов и токенизация увеличивают пик памяти.

`_DbVisitedSet` делает SELECT на каждую рассматриваемую ссылку, а новую/просроченную помечает посещённой **до скачивания**. Ошибка сети, OOM или потеря index batch не отменяют отметку: повтор обычно откладывается на сутки. После перезапуска in-memory очередь потеряна, а отметки в SQLite остаются. Нужны раздельные last_attempt/last_success и retry/backoff; для надёжного возобновления — таблица frontier со статусом/next_due. Не требуется внешний брокер.

Технические проблемы жизненного цикла:

| Место | Последствие | Минимальное направление исправления |
|---|---|---|
| `_loading()` без `finally` | Ошибка extractor оставляет `downloading=True`; join может ждать бесконечно | Сбрасывать флаг в finally, task_done также в finally |
| `join()` проверяет флаги и empty, но не join потоков | Гонки завершения; return в finally скрывает ошибки | Корректный учёт незавершённых задач, stop + join workers, не подавлять исключения |
| Планировщик запускает новый crawl каждый час без single-flight | Обходы накладываются, множат потоки/очереди и конкурируют за writer | Один активный crawl, пропуск/перенос следующего запуска |
| Seeds добавляются до запуска workers, очередь 5000 | Более 5000 подходящих новых seeds не поместятся | Запуск потребителей до наполнения либо потоковый/durable frontier |
| Полная очередь просто отбрасывает новые ссылки | Неполное покрытие, зависимость от порядка ссылок | Сохранение в frontier или контролируемый бюджет обхода |

Перекрытие — не только теоретический риск: в логах завершён один crawl за **2:00:56**, при расписании раз в час. Но бесконечное зависание из-за `_loading` в имеющихся логах не доказано.

В [rns_request.py](../src/core/crawler/rns_request.py#L42) на страницу создаются новый event loop и новый RNS.Link. Loop явно не закрывается, link не переиспользуется и не teardown-ится на успехе/ошибке/таймауте. Сброс ссылки на receipt в Document не закрывает сетевой link. У RNS есть собственные ссылки на активные links и keepalive; рассчитывать только на GC неправильно. Точный вклад этого удержания в production OOM не измерен.

Failed callback делает `raise RequestError` в чужом callback-контексте, но не завершает ожидающий `_AsyncWrapper`. Поэтому запрос может ждать весь внешний timeout 20 с даже после уже известной неудачи. Polling каждые 100 мс добавляет задержку обнаружения завершения на стадии handshake/ответа. Достаточно одного механизма ожидания — например threading.Event/Future — с доставкой и результата, и ошибки, и явным cleanup. Пул соединений стоит добавлять только с пределом числа links/idle TTL; сначала можно просто гарантировать закрытие.

**9. SQLite: движок подходит, отдельные запросы и транзакции — нет.**

Production `journal_mode=delete`. EXPLAIN QUERY PLAN и микрозамеры выполнены на backup-копии; ниже warm median пяти выполнений. Это время SQLite без ORM, fsync и конкурирующих writers.

| Запрос | Фактический план | Локальное время |
|---|---|---:|
| Nodes page, rank/time, 20 строк | SCAN nodes + TEMP B-TREE ORDER BY | 0.27 мс |
| Nodes `%test%`, 20 строк | SCAN nodes + TEMP B-TREE ORDER BY | 0.78 мс |
| Peers page, 20 строк | ordered scan idx_peers_time | 0.019 мс |
| Peers `%test%`, первые 20 | scan idx_peers_time с фильтром | 1.46 мс |
| 10 последних уникальных запросов | SCAN search_queries + TEMP B-TREE GROUP BY + ORDER BY | 0.98 мс |
| Поиск узла по dst | SEARCH unique index | 0.004 мс для отсутствующего dst |
| Citations по target | SEARCH idx_citations_target | 0.003 мс для отсутствующего target |

Нет оснований считать SQLite SELECT главным источником секундной задержки поиска: `_get_node_features` уже делает один bulk IN-запрос, а не N+1 на все кандидаты. Но в `views.search` есть до 20 отдельных find_node_by_address; каждый ещё вычисляет две gamma-квантили через `_node_to_dict`, хотя нужен только name. На странице nodes — по owner и citations на каждую строку, а get_amount_for выгружает все ссылки ради len.

Рекомендации по приоритету: пакетно получать name/owner/counts для отображаемой страницы; не рассчитывать survival внутри универсального преобразования Node, когда нужны только name/identity; COUNT вместо загрузки списка для количества ссылок. Индекс `(removed, rank DESC, time DESC)` устранит сортировку обычной страницы nodes; для `%substring%` обычный B-tree не решает поиск — нужен scan либо отдельный FTS/trigram-подход.

В `crawl_visited_urls` два одинаковых по назначению URL-индекса: UNIQUE уже создал autoindex, а `idx_crawl_visited_url` дублирует его. Каждый занимает **11 509 760 байт**, то есть один лишний индекс около 11 MiB плюс обновления на записи. Таблица visited с индексами — около 35.5 MiB, более половины SQLite. Удалять дублирующий индекс следует миграцией; место станет переиспользуемым, файл не обязательно сразу уменьшится. Полный VACUUM на загруженном VPS не нужен в горячем пути.

Announce на каждый event делает SELECT и отдельный commit. Каждая новая/просроченная visited-ссылка — отдельный commit. Каждый первый поиск и каждая идентифицированная страница поиска пишут историю. В rollback journal это усиливает случайные записи и конкуренцию. WAL позволяет readers и writer меньше мешать друг другу, но **writer всё ещё один**. Нужны короткие транзакции, ограниченная группировка фоновых updates и обработка busy, а не ожидание, что WAL устранит все блокировки. В скопированных логах `database is locked` не найдено: это рекомендуемое улучшение, не установленная причина текущих аварий. [SQLite WAL](https://www.sqlite.org/wal.html).

Latest queries на главной группирует всю растущую историю ради десяти строк. Сейчас 3811 строк — недорого. На будущее хранить отдельную агрегированную запись query→last_seen либо кэшировать результат; чтение «последних 100 строк и dedup» не даёт гарантированно последние 10 уникальных. Для history/visited/peers нужны осмысленные retention/архивирование, а не бесконечный рост по времени.

**10. Фоновые ранги: не главный bottleneck; есть ошибка семантики citations.**

PageRank реализован разреженными adjacency lists, без матрицы N×N. Сложность `O(E + I(V+E))`, память `O(V+E)`. `I ≤ 100`. Из логов production: вычислительная часть последних запусков 0.43–0.59 с для примерно 3527 узлов / 3742 активных рёбер. Запись рангов и другие этапы идут отдельно. Оптимизация через SciPy/Numba здесь сейчас не оправдана.

Локальная проверка `pagerank_impl` на реальном графе и его 3/5 независимых копиях, без искусственных sleep, median трёх запусков: 0.061 / 0.194 / 0.331 с. Это проверяет линейное масштабирование при сохранении структуры, но не гарантирует столько же итераций у будущего другого графа. По умолчанию ещё добавляется до 0.1 с sleep за 100 итераций.

Survival recalculation каждые 6 часов заново читает announce logs (~13 MiB в снимке), хранит массив timestamp на каждый узел и дважды сортирует события. `fit_site_params` при известном окне фактически использует только число событий. Достаточно потоковых счётчиков и earliest timestamp; массивы и сортировки не нужны. Если логов станет много, дневные агрегаты в SQLite заменят полный повторный разбор JSON. Текущие startup-логи показывают выполнение survival вместе с записью примерно за несколько секунд, а не основную постоянную задержку.

Gamma-квантили в rerank считаются дважды на каждый различный узел, на каждом cache miss. Их можно сохранять при обновлении alpha/beta; от текущего времени зависит дальнейшая дешёвая формула, а не сами квантили. Это вторичная оптимизация после подсветки и mmap, сохраняющая модель.

В [Citations.update_citations](../src/core/data/citations.py#L18) при разборе **одной страницы** удалёнными помечаются все ссылки того же узла, отсутствующие на этой странице. Следующая страница перезаписывает картину предыдущей: граф отражает последнюю обработанную страницу, а не объединение ссылок узла. Это портит ранжирование и создаёт лишние toggles/updates. Хранить provenance на уровне source page и агрегировать node graph либо заменять node citations только после полного успешного обхода узла. Дешёвое «никогда не удалять ссылки» оставит вечные устаревшие рёбра и не является полноценным исправлением.

**11. Проверенная сложность операций.**

Обозначения: `D` — живые документы, `B` — байты индексных подфайлов, `M` — совпадения запроса, `U` — адреса среди них, `R ≤ min(M, 2U)` — выдача после фильтров; `P=20`; `K` — кандидатный лимит; `E,V` — граф; `A` — announce-события; `Q` — история; `F` — visited URL; `Z` — глубина OFFSET. Стоимость postings зависит от частоты/типа термина, поэтому полнотекстовый поиск нельзя честно обозначить просто `O(log D)`.

| Операция | Время | Дополнительная память / замечание |
|---|---|---|
| Открытие searcher в текущем mmap-пути | O(B) копирования | O(B) heap + mapped pages; не зависит от M |
| BM25 `limit=None`, обычные terms | postings/scoring + до O(M log M) сортировки | O(M) результатов, плюс reader |
| Материализация всех hits | O(суммы загруженных stored bytes) | Декодирование целых полей; временные поля/объекты |
| Highlight всех hits | O(суммы токенов до charlimit по M), плюс query term expansion | Повторная токенизация; wildcard дороже простой формулы |
| URL/address filters | O(M), среднее для hash tables | O(M) / O(U) |
| Node features | примерно O(U log V) indexed probes + O(U) квантилей | O(U) |
| Rerank | O(R log R) | O(R) |
| Cache hit | O(R) копирования списка + O(P) отображения | O(R) ссылок; cache хранит до 200 выдач |
| Top-K | postings + до O(M log K), pruning зависит от запроса | O(K) кандидатов, не гарантированное O(K) CPU |
| Visited lookup/update | O(log F) на ссылку + commit latency при записи | Множится на число обнаруженных ссылок, не только страниц |
| Citations update страницы | O(log E + outdegree узла + ссылки страницы), плюс updates | Все существующие исходящие рёбра узла загружаются каждый раз |
| Nodes page без составного индекса | scan O(V), bounded sort до O(V log(P+Z)) | Глубокая OFFSET-пагинация дороже |
| Peers page без фильтра | O(log peers + Z + P) | Используется индекс времени |
| `%substring%` + count | O(числа строк × стоимости проверки строки) | LIMIT может раньше остановить page query, не count |
| Latest unique queries | scan/group до O(Q log Q), sort групп/top limit | Индекс created_at не устраняет GROUP BY query |
| Full optimize | Чтение/перезапись живого индекса, примерно O(B + postings) | Повтор каждые 250 страниц даёт сверхлинейный суммарный расход |
| PageRank | O(E + I(V+E)) | O(V+E), не O(V²) |
| Survival recalculation сейчас | O(A + Σ aᵢ log aᵢ + V) | O(A+V); счётчики позволяют O(A+V) time, O(V) memory |

В sparse PageRank суммарное время не O(E) без оговорок: есть проходы по всем V и до I итераций. В SQL `SCAN ... USING INDEX` не равнозначно дешёвому поиску по ключу: с фильтром оно может прочитать много строк.

**12. Что произойдёт при росте ×3 и ×5.**

Модель сохраняет распределение размеров страниц, долю совпадений и отношение числа обновлений к размеру корпуса. Реальная сеть может расти иначе, особенно за счёт больших сайтов; тогда предсказания нужно пересчитать.

| Показатель | Сейчас | ×3 | ×5 |
|---|---:|---:|---:|
| Живые страницы | 14 198 | 42 594 | 70 990 |
| Известные активные узлы при пропорциональном росте | 3 527 | 10 581 | 17 635 |
| Индекс, грубая модель | 263 MiB | 789 MiB | 1 315 MiB |
| Heap-копия при открытии текущего mmap reader | 239 MiB | ~717 MiB | ~1195 MiB |
| Совпадения `network`, модель | 2 696 | ~8 088 | ~13 480 |
| CPU/latency `network` текущего pipeline, локальный ориентир без swap | 1.65 с | ~5 с | ~8 с |
| CPU/latency широкого `page`, тот же ориентир | 8.1 с | ~24 с | ~41 с |
| Полные merges на условный полный recrawl | ~57 | ~171 | ~284 |
| Их write volume при стабильном размере индекса | ~15 GiB | ~132 GiB | ~365 GiB |

Последние две строки — намеренно условный полный recrawl, не утверждение, что сегодня столько пишется каждые сутки. Фактические обходы часто значительно меньше из-за visited/таймаутов/неполного покрытия.

Для пяти сетевых workers и среднего времени загрузки `t` нижняя оценка полного успешного обхода `D*t/5`, без SQL, индексации, дедупликации и ожидания writer:

| Среднее t | 14 198 страниц | ×3 | ×5 |
|---|---:|---:|---:|
| 1 с | 47 мин | 2.4 ч | 3.9 ч |
| 5 с | 3.9 ч | 11.8 ч | 19.7 ч |
| 20 с, таймаутный сценарий | 15.8 ч | 47.3 ч | 78.9 ч |

20 секунд — сценарий множества неудачных загрузок, а не ожидаемое среднее всех страниц. Тем не менее расписание «каждый час запускаем новые пять потоков» не задаёт безопасный предел нагрузки. На ×5 при пятисекундном среднем даже идеализированный recrawl почти занимает сутки; нужен инкрементальный next_due, backoff и приоритет страниц, а не попытки ежедневно перечитать всё любой ценой.

После mmap fix и поздней подсветки обработка кандидатов остаётся зависимой от корпуса, но дорогая подсветка — только от P. По локальным измерениям `network` около 0.1 с, широкий `page` около 0.5 с; при линейном росте кандидатов ×5 это скорее порядок 0.5–2.5 с на той же локальной машине, не на VPS. Top-K ограничивает объём последующего rerank/материализации, но postings и дорогой parser всё ещё требуют контроля.

**Оценка пригодности железа:** на нынешнем shared gateway 454 MiB текущий код уже непригоден для стабильной работы — это наблюдение, а не прогноз. С исправлениями 14 тысяч небольших документов и редкие запросы посильны одному CPU, но RAM всё равно нужно делить с rnsd и прочими сервисами. Для 40–70 тысяч страниц 0.5 GiB нельзя обещать как рабочую конфигурацию этого набора сервисов. Практический старт проверки: отдельное размещение приложения либо 1 GiB для минимального выделенного экземпляра, около 2 GiB для совмещённого хоста; это бюджетная гипотеза для измерений, не гарантированный минимальный размер. Второй CPU помогает параллельной индексации/транспорту, но устранение лишней работы важнее. Увеличение swap не заменяет RAM.

**13. Архитектурные варианты, от меньших изменений к большим.**

**A. Оставить Whoosh + SQLite.** Наименьший риск для функциональности. Отключить mmap, поздно подсвечивать, уменьшить writer pool, убрать частые optimize, один crawl, строгая проверка URL, исправить cleanup/ошибки, WAL и пакетные metadata queries. PageRank оставить. Query cache уменьшить по памяти. Это первый рекомендуемый этап, достаточный для проверки жизнеспособности текущей нагрузки.

**B. Разделить serving и crawl/indexing.** Поиск и выдача не должны конкурировать с тяжёлыми merge и сетевым обходом за непредсказуемый объём памяти. На более просторной машине можно отделить crawler в процесс с ограничением ресурсов; один writer обслуживает индекс, readers работают с опубликованным поколением. На 454 MiB несколько Python-процессов могут сделать хуже, поэтому полезнее вынести crawler/indexer на другой хост. Передавать gateway готовые неизменяемые поколения индекса и соответствующие metadata, переключая их атомарно. Нельзя синхронизировать живые частично записанные файлы или отдельно несовместимые версии рангов/индекса. Альтернатива — перенести всю поисковую службу, сохранив gateway транспортным узлом. Remote SQLite по сетевой FS не подходит для WAL.

**C. SQLite FTS5 вместо Whoosh.** Подходящий кандидат для малого сервера: встроенный в SQLite inverted index и BM25, меньше Python-работы и одна система хранения для pages/metadata/frontier. Проверен маленький локальный прототип на всех 14 198 живых страницах: FTS-таблица с porter/unicode61, text+nodeName, stored URL/address/owner. Создание заняло 1.2 с; файл около 89 MiB. SQL top-200 по weighted BM25: `reticulum` 2.0 мс, `test` 1.4 мс, `network` 2.0 мс, `page` 5.7 мс. Отдельные snippets первых 20 — соответственно примерно 2.2 / 0.6 / 2.0 / 83 мс: большой документ всё ещё может дорого подсвечиваться.

Это **не эквивалентный заменитель готового поиска**: прототип не индексирует URL/owner/address для поиска, не воспроизводит ngram nodeName, custom regex анализатора, полный rerank, разнообразие адресов и всю query syntax. Поэтому нельзя обещать 800-кратное ускорение продукта делением этих цифр на время текущего end-to-end pipeline. Прототип показывает, что FTS5 стоит рассмотреть, если после точечных исправлений хочется упростить хранение и избежать Python-движка. Нужны dual-index/replay на наборе запросов и управляемая миграция с сохранением старого индекса для отката. [Официальная документация FTS5](https://www.sqlite.org/fts5.html).

Отдельный Elasticsearch/OpenSearch, кластер или vector search для 14–70 тысяч таких страниц и наблюдаемой частоты запросов не обоснованы. Нужный эффект уже показан изменением порядка работы и настройки существующего хранилища. Выбирать другой серверный движок следует при измеренной потребности в сложной релевантности/параллельном throughput, а не по самому факту роста D.

**14. Предлагаемый порядок работ и критерии завершения.**

| Приоритет | Изменение | Как проверить |
|---|---|---|
| P0 | `supports_mmap=False` | Свежий процесс, RSS до/после searcher; тот же набор результатов; контроль full crawl/merge |
| P0 | Highlight после rerank и выбора страницы | Совпадение URL/order/числа результатов; проверка нескольких страниц и snapshots индекса |
| P0 | Single crawl, cleanup links/loops, finally/task_done, сохранение batch при ошибке | Сбой downloader/extractor/writer не оставляет вечных потоков и не теряет задания |
| P0 | Ограничения запроса/размера ответа/параллелизма; фильтр URL до visited | `*`, длинные выражения, HTTP URL и слишком большие страницы не запускают неограниченную работу |
| P1 | Убрать частые optimize, hash изменений, контролировать writer pool/batch bytes | Число commits/merge, MB written, пиковая память и время обновления |
| P1 | Исправить citations по source page и visited/retry semantics | Две страницы одного узла дают объединение ссылок; неудача доступна для retry |
| P1 | WAL, bulk metadata, лишний индекс, ограниченный cache | EXPLAIN, busy/commit latency, cache bytes; отсутствие замены функциональности эвристикой |
| P2 | FTS5 или вынос crawler/службы; top-K при необходимости | Сравнение качества, памяти, latency на ×3/×5 и реальном сетевом контуре |

Добавить короткие тайминги: parse/open/collect/stored/highlight/rerank/render; число кандидатов, cache hits/bytes, crawl queue/retries, active links/threads, writer duration/bytes. На сервере мониторить RSS **и VmSwap**, system memory/IO PSI, swap-in/out и OOM, а не только текущий RSS раз в пять минут. Текущие логи не позволяют восстановить честный production p95 поиска.

После изменений: локальный набор обычных, широких и некорректных запросов; одновременный controlled crawl и запросы; затем наблюдение минимум полного цикла crawl плюс scheduled jobs. Стартовый критерий — отсутствие OOM и устойчивого swap churn, ограниченные очереди/links, отсутствие потери заданий, сохранение качества. SLA пользовательского ответа задавать отдельно для CPU-части и Reticulum RTT. Ранний ориентир для CPU-части — p95 менее секунды на типичных запросах при фоне; это цель проверки, а не уже достигнутый результат на gateway.

**Артефакты и воспроизведение.**

[probe.py](performance-audit/probe.py) запускается только на локальной копии `search_index/` и `nomadapi.db`, не стартует Reticulum и не вызывает writer. Он сравнивает полный pipeline, позднюю подсветку и top-200, проверяя assert-ами сохранение top-20/числа результатов у поздней подсветки. `--mmap` воспроизводит потребление памяти исходного варианта и требует достаточной RAM. Не запускать этот режим на текущем gateway.

```sh
OPENBLAS_NUM_THREADS=1 /tmp/waystone-audit/venv311/bin/python \
  docs/performance-audit/probe.py /tmp/waystone-audit
# Исходный вариант хранения, только на машине с запасом RAM:
OPENBLAS_NUM_THREADS=1 /tmp/waystone-audit/venv311/bin/python \
  docs/performance-audit/probe.py /tmp/waystone-audit --mmap --query network
# Отдельный процесс для проверки главной причины расхода памяти:
OPENBLAS_NUM_THREADS=1 /tmp/waystone-audit/venv311/bin/python \
  docs/performance-audit/probe.py /tmp/waystone-audit --memory --mmap
# Повторить без --mmap для сравнения.
```

Для нового окружения нужны Python 3.10/3.11 и зависимости проекта; в эксперименте версии NumPy/SciPy совпадали с production. Python 3.14 не использовался для измерений: текущий Config несовместим с его обработкой annotations без отдельной правки.
